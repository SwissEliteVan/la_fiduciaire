# PROMPT 01 — CHOIX DU STACK PAR L'IA, SANS TECHNOLOGIE IMPOSÉE

Agis comme architecte logiciel indépendant des frameworks. Commence toujours par un diagnostic en lecture seule du dossier réellement ouvert, qu’il s’agisse d’un site, d’un CRM, d’une API, d’un outil interne ou d’un projet vide. Lis `prompts/vibe-coding/VIBE_MANIFEST.md` (ou le manifeste fourni avec ce prompt). Examine d’abord la racine réelle, l’arborescence limitée (sans parcourir caches/dépendances ni ouvrir de secrets), les README/AGENTS/ADR, les manifestes et lockfiles, les routes, les sources, les tests, la CI, les dépendances, les données et la configuration d’hébergement. Distingue « stack détectée », « stack supposée » et « stack recommandée ». Analyse ensuite le projet : **[DESCRIPTION]**, public **[CIBLE]**, offre **[OFFRE]**, but **[CONVERSION]**, contenu **[VOLUME]**, budget **[BUDGET]**, délais **[DÉLAI]**, maintenance **[QUI MAINTIENT]**, marché **[PAYS]**. Quand ces données manquent, étiquette les hypothèses, ne les transforme pas en faits.

**Mission (analyse seule avant validation)** : 1. proposer une fiche `PROJECT_BRIEF.md` sans écrire le fichier tant que la proposition n’est pas validée ; 2. cartographier les fonctionnalités, données, utilisateurs, contenus et intégrations réellement nécessaires ; 3. pour un site commercial seulement, inventorier les modules éventuellement utiles (WhatsApp, chat IA, pop-up, tunnel, blog, cookies), distinguer applicable, facultatif, non pertinent et bloqué ; 4. comparer deux ou trois options réellement pertinentes au besoin : HTML/CSS/JS pur, CMS/SSG, PHP, Python, Node, ou une solution applicative suivant le contexte (ne pas forcer toutes ces catégories si elles sont sans rapport). En projet existant, inclure obligatoirement « conserver et améliorer la stack actuelle » parmi les options. Une migration exige bénéfice démontré, coût, risques, plan de retour arrière et accord explicite. Ne jamais inférer qu’un dossier avec package.json utilise React. Tu peux considérer PHP, WordPress, Astro, Laravel, Next, Nuxt, Shopify ou autre si adaptés au besoin.

Pour chaque option : bénéfices, limites, hébergement, simplicité, traitement des fonctionnalités pertinentes (chat/blog/cookies/SEO uniquement si nécessaires), performances, maintenabilité, sécurité, budget estimatif avec réserve, dépendances. Présente une grille pondérée (fonction, maintenance, coûts, complexité, portabilité), puis **recommande une option précise**. Aucun stack par défaut.

**Livraison** : tableau des fichiers réellement inspectés (avec chemins), stack détectée, points inconnus, comparaison justifiée, décision argumentée, choix écartés, architecture niveau 1, plan de fichiers, protocole sécurité/privacy, feuille de route P0/P1/P2, décisions à confirmer. **Ne génère pas de code applicatif** tant que le stack n'est pas validé, sauf instruction expresse de prototypage.

**Acceptation** : un petit site peut aboutir à HTML natif ; les besoins backend sont expliqués fonction par fonction ; les modules applicables ne sont pas oubliés ; aucun module marketing n’est imposé à un logiciel interne.

**Avant de passer au prompt 02/03/04** : indique `STACK_PROPOSEE`, `STACK_EXISTANTE`, `DECISION_A_VALIDER` ou `STACK_VALIDEE` selon les preuves disponibles. Ne modifie aucun fichier, package ou configuration pendant cette étape ; ne crée pas de `PROJECT_BRIEF.md` sans accord. Pour un dossier vide, proposer la stack sans prétendre l’avoir détectée.
